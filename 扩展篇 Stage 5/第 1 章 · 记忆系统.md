# 第 1 章 · 记忆系统：分层、分布式与防污染

> **为什么有这章**：原项目记忆只有 ConversationMemory（本地）+ DistributedMemory（Redis）——对话历史往 Redis 一存就完事，太扁平：没分层（全靠对话历史，又贵又会爆）、没防污染（写入不过滤）、多租户也没强制隔离。这章补成**记忆三层（热/归档/情景）+ 防污染闸（写入前扫描 / Session 内冻结快照 / write-then-index）+ 按租户隔离**；对应学员反馈"存储记忆太简单、'具体怎么存的'答不上来"、面试连环追问"记忆存哪 / 多 Agent 并发写 / 跨实例续接 / 会不会被污染"。

## 这篇讲什么

记忆系统要解决的问题是：**长期要记住的东西存哪、用的时候怎么取回、怎么不被恶意污染**——不能全塞进上下文（贵、会爆、模型对中间内容"Lost in the Middle"），也不能存在外面就再也找不回来。

为什么服务端要单拎出来讲：本机的 Claude Code / OpenClaw / Hermes 是单用户工具，记忆往自己电脑上的 MEMORY.md / SQLite 一丢就完事，一个开发者只管自己；我们是多租户共用服务端存储，A 租户的记忆绝不能被 B 读到，所以记忆 key、向量 collection 都得强制带 tenantId 切分。这是这章和本机工具最大的不同。

**核心模型：记忆三层 + 防污染闸。** 信息按"怎么被访问"分三层存放，写入时再过一道防污染闸：

**三个关键认知（想通这三个，这章就懂了）：**

- **上下文是 RAM，不是存储**：分层不是为分而分，是因为全塞进 context 又贵又会"Lost in the Middle"。热记忆小上限（~800T）反直觉但正确——上限一大就退化成垃圾桶，还破坏 Prefix Cache。决定"什么留 / 什么放外面 / 怎么取回"才是记忆系统的本质。

- **按访问模式分层，不是按数据类型**：始终要用的（热）零延迟注入；可能相关的（归档）不自动注入，让 Agent 主动检索——防系统提示随时间膨胀；经验类（情景）走 Skill 渐进式披露（平时只载名称，用得着再展开全文）。混在一起是大多数记忆系统不可靠的根因。

- **记忆污染比记忆缺失更危险**：它静默、持续、会扩散——ClawHavoc 实例里恶意 Skill 把指令写进 MEMORY.md，跨 Session 永久控制 Agent。所以写入前扫 4 类威胁、Session 内系统提示冻结（被诱导写入也只下次生效，留发现窗口）、write-then-index（写失败不更新索引）——三道缺一就有漏洞。

> 这是这章的骨架。每层具体怎么存、关键实现示例代码长什么样，往下看 §1.2 起。**细节是用来查的，不用全记**；先把上面这个三层模型和三个认知想清楚。

**一句话认知（贯穿全章）**：**上下文是 RAM，不是存储。** 把什么都塞进 context，就像把所有数据都放内存——又贵又会爆。记忆系统的本质是给信息分层，让大部分待在外部存储，只把当前需要的换进 context。

## 1.2 理论基础：记忆的四个层次

三大 Agent 的记忆设计再千差万别，都建立在这同一个理论框架上：

| **层次** | **说明** | **访问 / 容量** |
| --- | --- | --- |
| **① 上下文记忆 In-context** | 当前 token 窗口里的全部内容 | 访问免费 容量小 会话结束即消失 |
| **② 外部记忆 External** | 持久化在模型外 文件/DB/向量库 | 访问需检索 容量大 跨会话存活 |
| **③ 情景记忆 Episodic** | 过去行为的结构化记录 做过什么/怎么做/结果 | 访问需检索 Agent 从经验学习的基础 |
| **④ 参数记忆 Parametric** | 模型训练权重里编码的知识 | 访问免费 运行时不可改 有幻觉 |

三框架的分歧 100% 集中在 ② 外部记忆 和 ③ 情景记忆 怎么设计。

| **层次** | **谁负责（AgentForge 对应）** | **教学价值** |
| --- | --- | --- |
| **① 上下文** | ReACT 循环里的 chatHistory | 理解"为什么不能全塞" |
| **② 外部** | Redis（会话历史）+ Milvus（长期语义） | 本章核心：分层检索 |
| **③ 情景** | SkillManager（成功执行路径沉淀为 Skill） | 衔接第 5 章 Skill 按需加载 |
| **④ 参数** | LLM 自身（不归我们管） | 边界认知：有些"知识"改不了 |

### 1.3.1 OpenClaw —— 文件即真理

**哲学**：没有写进文件的，不存在。所有长期状态持久化为磁盘 Markdown；文件既是存储介质，也是人机协作接口。

```Plaintext
~/.openclaw/workspace/
├── MEMORY.md          ← 长期精华（每次会话都加载）
├── SOUL.md            ← Agent 身份定义
└── memory/
    ├── 2026-07-16.md  ← 今日日志（今天自动注入）
    ├── 2026-07-15.md  ← 昨日日志（昨天自动注入）
    └── 2026-07-14.md  ← 更早：不注入，靠检索访问
```

### 1.3.2 Claude Code —— 上下文工程优先

**哲学**：不追求存更多，追求**在正确时机注入正确信息**。上下文容量 ≠ 可用容量（Lost in the Middle：头尾强、中间弱）。记忆架构是"Token 预算分配 + 信息注入机制"，不是存储系统。

**分层 CLAUDE.md——用路径编码相关性**：

```Plaintext
~/.claude/CLAUDE.md           ← 用户级：所有项目都加载
~/project/CLAUDE.md           ← 项目级：进入项目加载
~/project/src/CLAUDE.md       ← 目录级：进入该目录加载

→ 当前工作目录在哪，文件系统路径本身就决定加载哪些规则
→ 用 O(1) 的路径查找，替代了语义检索
   代价：只能静态"这个目录用什么规则"，不能动态"这个任务需要什么知识"
```

### 1.3.3 Hermes —— 四层分离，情景记忆为核心

**哲学**：不同访问模式的记忆，必须在**不同的存储介质**里、用**不同的方式**管理。混在一起是大多数 Agent 记忆系统不可靠的根因。

| **层** | **存储** | **访问方式** |
| --- | --- | --- |
| **① 热记忆** | MEMORY.md ~800T / USER.md ~500T 小上限强制质量控制 | 始终注入 零延迟 Prefix Cache 命中率高 |
| **② 历史归档** | SQLite + FTS5 全文索引 | 不自动注入 Agent 主动 session_search 召回→轻量摘要→注入 |
| **③ 情景记忆** | ~/.hermes/skills/*.md 存经验非事实 | ≥5 次工具调用自动沉淀 渐进式披露 + 自我更新 |
| **④ 用户建模** | Honcho（可选） | 用户怎么思考的持久模型 |

### 1.3.4 三框架的记忆防线：污染与压缩

**记忆污染比记忆缺失更危险**——它静默、持续、会扩散。**ClawHavoc 事件**（OpenClaw 被攻破）：

<!-- 画板未能抓取（请把画板滚动到可见区域后重试，或在飞书里另存为图片手动插入） -->

**三框架的防污染对比**：

| **防线** | **OpenClaw** | **Claude Code** | **Hermes** |
| --- | --- | --- | --- |
| **写入权限** | 完全交给模型（被攻破） | 交给用户（需确认） | 程序级过滤器 |
| **写入门控** | 无 | write-then-index + `/remember` 用户审批 | `_scan_memory_content` 写入前扫描 |
| **记忆结构** | MEMORY.md 存全部内容 | MEMORY.md 只作**索引**（指针），内容在 topic 文件 | 存内容但有容量上限 + **冻结快照** |
| **关键机制** | （缺失） | 成功完成写入后才更新索引（防记失败操作） | 写入前扫 4 类威胁；Session 内系统提示冻结 |

> **冻结快照**（Hermes）：记忆在 Session 开始时作为快照注入系统提示，中途的写入只落盘、**不改当前 Session 的系统提示**——即便中途被诱导写入恶意记忆，当前 Session 不受影响（下次才生效），给用户发现窗口；同时系统提示整段不变 → Prefix Cache 命中率最大化（安全 + 性能双赢）。

**上下文压缩策略对比**：

| **维度** | **Claude Code** | **Hermes** | **OpenClaw** |
| --- | --- | --- | --- |
| **层数** | 五层级联 | 单类单策略 | 无内置（靠重启） |
| **廉价预处理** | Microcompact（5 万字符阈值，纯数学，超了写盘+2KB 预览） | preflight 字符估算 | — |
| **深度压缩** | AutoCompact（70% 触发，LLM 摘要）+ 后台 Session Memory 子 Agent | 5 字段模板增量摘要 | — |
| **兜底** | Context Collapse（非破坏性） | 冻结快照保证 | 30 分钟心跳"干净重启" |

## 1.4 选型：服务端多租户语境下的取舍

> 这是与"照搬 Claude Code 教程"的分水岭。**部署形态决定哪些设计能用。**

| **维度** | **三大 Agent（本机 单用户 dev-tool）** | **AgentForge（我们是服务端 多租户 平台 类豆包）** |
| --- | --- | --- |
| **用户规模** | 一个开发者 | 成千上万租户 |
| **workspace** | 一个本地 workspace | 共享服务端存储 |
| **记忆** | 本地 MEMORY.md 文件 | Redis/Milvus 按租户隔离 |
| **工具** | 本地 shell/文件/git | 业务 API / 企业系统 |
| **会话** | 单会话 | 多租户 多会话 高并发 |

逐框架判断（每个都要回答"搬到服务端多租户，能用吗"）：

| **框架做法** | **本机前提** | **搬到服务端多租户** | **判定** |
| --- | --- | --- | --- |
| **OpenClaw 文件即真理** | 一个用户一个本地 workspace | 不可能每租户一个本地文件 | **弃**（取其混合检索、Memory Flush 思想） |
| **OpenClaw 混合检索（语义+BM25）** | sqlite-vec 本地 | 思想通用，换 Milvus+关键词 | **搬**（思想） |
| **Claude Code 分层 CLAUDE.md 路径查找** | 有"当前工作目录" | 服务端无工作目录概念 | **弃** |
| **Claude Code Token 三档预警 + 用量注入** | 与部署无关 | 通用工程经验 | **搬**（直接用） |
| **Claude Code 五层压缩** | 与部署无关 | 通用 | **搬**（取其工程思路） |
| **Hermes 四层分离（按访问模式分）** | 本地文件实现 | 思想通用，介质换分布式 | **搬**（作骨架） |
| **Hermes 写入前扫描 + 冻结快照** | 与部署无关 | 通用安全机制 | **搬**（直接用） |
| **Hermes 情景记忆 Skills** | 本地 skills 目录 | 已有 SkillManager（声明式） | **搬**（已有骨架，加自动沉淀） |

**选型结论**：

```Plaintext
骨架：Hermes 四层分离（按访问模式分层）
   + 工程：Claude Code 的 Token 预算 / 三档压缩 / 用量注入推理
   + 安全：三框架的防污染（写入前扫描 + 冻结快照 + write-then-index）
   + 思想：OpenClaw 的混合检索 + Memory Flush（落盘防丢）
   弃：OpenClaw 文件存储 / Claude Code 路径查找（本机专属）
```

> 三大权重印证总纲：OpenClaw/Hermes（服务端可部署）的做法被大量采纳；Claude Code 贡献的是与部署无关的通用工程经验。

### 1.6.3 分布式会话记忆（关键实现示例）

> 服务端多租户下，会话历史必须在 Redis，多实例按 sessionId 续接。`BaseAgent.chat` 入口做分布式回填 + 热记忆冻结注入。

**Java（BaseAgent）**：

```Java
public String chat(String tenantId, String sessionId, String userInput) {
    // 1. 会话开始：注入热记忆（冻结快照——之后不变，利于 Prefix Cache）
    if (!sessionInitialized) {
        systemPrompt += memory.loadHot(tenantId, agentId);   // Redis，小上限
        sessionInitialized = true;
    }
    // 2. 分布式回填：本地不新鲜则从 Redis 拉最近 N 轮（多实例续接）
    if (!memory.isFresh(tenantId, sessionId)) {
        memory.backfillFromDistributed(tenantId, sessionId, recentN);
    }
    // 3. ReACT 循环（声明式核心，不变）……
    // 4. Token 预算感知：用量注入系统提示 + 三档预警 70/85/90%
    // 5. 新消息持久化：写入前扫描（防污染）→ Redis
}
```

```Python
# Python：异步完成热记忆注入、跨实例回填与持久化
async def chat(self, tenant_id: str, session_id: str, user_input: str) -> str:
    # 首次进入会话时冻结热记忆快照，避免后续改动破坏 Prompt 前缀缓存。
    if not self.session_initialized:
        hot_memory = await self.memory.load_hot(tenant_id, self.id)
        self.system_prompt += hot_memory
        self.session_initialized = True

    # 当前实例的缓存不是最新时，从 Redis 回填最近 N 轮，使请求可跨实例续接。
    if not await self.memory.is_fresh(tenant_id, session_id):
        await self.memory.backfill_from_distributed(
            tenant_id, session_id, self.recent_n
        )

    # 省略 ReAct 循环：循环中持续检查 Token 水位并输出三档预警。
    answer = await self._run_react(user_input)

    # 写入共享存储前先做污染扫描，避免恶意内容进入后续会话记忆。
    await self.memory.append_safe(tenant_id, session_id, user_input, answer)
    return answer
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **多实例续接** | 本地不新鲜 → Redis 回填最近 N 轮 | "分布式多实例怎么共享会话"的标准答法 |
| **热记忆冻结** | 仅会话开始注入，之后不变 | 安全窗口 + Prefix Cache 命中双赢 |
| **多租户** | 所有读写强制带 tenantId | 防 A 租户读 B 租户会话 |

### 1.6.4 结构化压缩 + 三档预警（关键实现示例）

主线压缩是拼字符串。升级为 Hermes 式 5 字段结构化增量摘要 + Claude Code 三档预警：

## 小结

1. **记忆本质是分层**：上下文是 RAM 不是存储；按访问模式分热/归档/情景三层（Hermes 骨架）。

1. **服务端多租户是分水岭**：本机文件方案（OpenClaw）直接弃，换 Redis/Milvus 按 tenant 隔离。

1. **三大 Agent 各取所长**：Hermes 分层 + Claude Code Token 工程 + 三框架防污染。

1. **防污染是必考**：写入前扫描 + 冻结快照 + write-then-index，对应 ClawHavoc 真实案例。

1. **声明式核心不变**：三层都通过 `AgentConfig.memory` + etcd 动态下发，声明式卖点是地基。
