# 第 4 章 · 资源控制：Token 预算 + 令牌桶 + 熔断 + 死循环兜底

> **为什么有这章**：原项目资源控制只有一道令牌桶限流（按请求数）+ ReAct 上限 10 次——挡得住"请求太多"，挡不住"一次调用烧穿账单"和"一个租户死循环拖垮共享算力"。这章补成四道闸（+Token 预算 + 熔断 + 活跃度超时），把限流升级成"成本+公平+可用性三合一"护栏；对应学员反馈"算力/资源控制"、面试最爱拷的"多租户一个租户跑飞怎么办"。

## 这篇讲什么

资源控制要解决的问题是：**一次调用花多少、一个任务跑多久、什么时候该喊停**——别让单次调用烧穿账单，也别让一个失控的循环拖垮整个平台。

为什么服务端要单拎出来讲：本机的 Claude Code 这类工具，烧的是开发者自己的钱，资源控制只管"省钱"就够；我们是多租户共用算力，一个租户失控会挤占所有人（noisy neighbor），所以成本、公平、可用性三块都得管。这是这章和本机工具最大的不同。

**核心模型：四道闸。** 请求进来依次过四道闸，每道挡一类问题：

```Plaintext
请求 → 闸①限流(令牌桶,已有) → 闸②Token预算(TPM,新) → 闸③迭代预算+熔断 → 闸④活跃度超时 → Agent
        按租户                  超了降级            死循环三层兜底       不误杀长任务
```

**三个关键认知（想通这三个，这章就懂了）：**

- **死循环靠三层兜底，不是一道**：迭代预算硬顶（即使每轮都成功也不能无限跑）、连续失败熔断（工具反复失败就停）、活跃度超时（卡死才杀）。三层各防一种失控，缺一就有漏洞。

- **阈值用生产数据反推，不拍脑袋**：熔断取 3 次，是因为 Claude Code 团队从 BigQuery 里发现过真实事故——一个会话连续重试 3272 次、每天浪费 25 万次调用，之后才定的这个数。知道由来，比背"3"理解得深。

- **服务端独有"公平性"这一维**：本机工具只管成本，我们还得保证一个租户吃不满别人——所以按租户配额隔离。这一层是本机工具没有的。

> 这是这章的骨架。每道闸具体怎么实现、代码长什么样，往下看 §4.2 起。**细节是用来查的，不用全记**；先把上面这个模型和三个认知想清楚。

而"失控"是另一条线——和成本无关，是 Agent **停不下来**：

```Plaintext
失控的两个面：
   面A【无限循环】  工具反复失败 → Agent 反复试 → 永不收敛（烧钱）
   面B【卡死】      等一个永远不回的慢 API → 占着会话不动（占资源）

  → 成本护栏治"烧钱"；失控兜底治"停不下来"。两者都要，缺一个就被面试官追到底。
```

### 4.2.2 OpenClaw —— 全量加载 + 多模型 Fallback（成本线性膨胀）

OpenClaw 的成本哲学：**不主动优化 Token，只在"模型选择"这一个维度留杠杆**，省钱责任外包给用户。

```Plaintext
OpenClaw 成本模型：
   工具 Schema ──全量注入──▶ 连几个 MCP，全部 schema 每次常驻
                              （社区实测 5-6 个 MCP 后明显挤压推理预算）
   心跳       ──30 分钟一次──▶ 每次带完整 SOUL.md/AGENTS.md/MEMORY.md
                              默认配置每天 ~7.5 万 Token 空转
   省钱杠杆   ──只有"多模型 Fallback"──▶ 主模型限流就降级到便宜模型
                              （moonshot/kimi、ollama/qwen3:8b）
                              但要手动配路由，框架不自动判断
```

失控兜底：失败信息注入上下文，**模型自决**重试/换法/上报——**无内置重试上限、无强制上报**。已知生产症状：模型"默默绕路"用相近任务替代失败任务，再自信汇报"完成"。

```Plaintext
OpenClaw 失控防护：
   重试上限 ──无──▶ 全靠模型自觉
   熔断     ──无──▶ 工具一直失败会一直试
   超时     ──无──▶（靠 Heartbeat 旁路，不卡会话）
   → 反面教材：省钱和防失控都押注模型判断
```

> 教学点：OpenClaw 的"最大能力 + 默认开放"在资源控制上同样体现——**把成本和失控的责任都外包给最不懂的用户**。对本机 dev-tool 还行，对服务端平台是灾难。

### 4.2.3 Claude Code —— 三层自动省钱 + 自愈熔断（工程范本）

Claude Code 的核心：**省钱默认即生效，不用用户配**；失控用**真实生产数据反推的熔断阈值**兜底。

**三层省钱**：

```Plaintext
[层1] Prompt Cache（缓存前缀稳定）
   系统提示在 Session 开始冻结，整个 Session 不改
   命中缓存 ──只付原价 10%──▶
   一字之差 ──前缀失效──▶ 后续全按原价（极度敏感）
   Branch8 六个月实测：$2,400/月 → $680/月（-72%），质量不变
                       其中 Prompt Cache 贡献 ~90% 重复 Token 节省
   已知坑：2026-03 Anthropic 缓存 bug（GitHub #40524）致 Token 膨胀 10-20 倍

[层2] Auto-Compact（上下文自动压缩）
   达有效窗口 70% ──自动压缩成摘要──▶
   三级阈值 70% / 90% / 98%（成本控制连续化，不是撞墙才处理）
   有效窗口预留 20,000 Token 给摘要本身（最紧张也能压出来）

[层3] defer_loading（工具 Schema 按需付）
   Session 开始只载工具【名称列表】（极少 Token）
   真正调用某工具时才载它的完整 Schema
   接 200 个工具，平时只付名称 Token
   → 把 Schema 成本从"全量预付"变"按需支付"
```

**自愈熔断**：

```Plaintext
2026 年 2 月 BigQuery 发现的真实故障：
   1,279 个会话出现 50 次以上连续 Compaction 失败
   单会话最多重试 3,272 次
   每天浪费 ~25 万次 API 调用

   修复 ──▶ MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
              连续失败 >3 次 ──停重试、上报用户──▶

   → 关键：阈值不是拍脑袋，是用【生产日志反推】的（面试加分点）
```

> 教学点：Claude Code 给出两个黄金范式——① 省钱写进默认（用户无感）；② 熔断阈值用真实故障数据标定，不是经验值。

### 4.2.4 Hermes —— 迭代预算硬约束 + preflight 预检 + 200+ 模型路由

Hermes 把"防失控"编码进执行循环本身（迭代预算），把"省钱"做到极致（200+ 模型端点任选）。

**迭代预算**：

```Plaintext
Hermes 迭代预算（默认上限 90 次工具调用）：

   → 不是到顶才停，是提前预警（梯度警告）
```

### 4.2.5 工具数量的陷阱：工具越多 Agent 越强？错

Anthropic 工具设计指南的量化结论——**同时进上下文的工具 >5-10 个，系统性拉低决策质量**，同时线性推高 Token 成本：

```Plaintext
工具数量 vs 决策质量（Anthropic 数据）：
   工具数:    1-5      5-10      >10
   决策质量:  高       开始降    系统性下降（选错工具概率↑）
   Token:     小       中        线性膨胀（"工具税"）

   极端案例：
   4 个 MCP 服务器 schema 吃掉 150,000+ Token
   GitHub MCP 单服 43 个工具
   5 服务器 MCP = 99 工具 ≈ 134,000 Token ≈ 0.4 美元/调用
                                    20 轮推理 ≈ 8 美元（一个任务！）
```

三大 Agent 的应对（架构层 > 提示词层）：

```Plaintext
Claude Code ──架构层 defer_loading + Tool Search（语义搜索定位工具）
OpenClaw    ──提示词层 SOUL.md 软约束（用户自觉，无硬约束）
Hermes      ──Skills 按需激活（任务相关才进上下文）+ 多模型路由切片

→ Claude Code 的"先发现、再加载"两阶段是最干净的架构解
  （第 5 章 Skill 渐进式披露会展开，本章只点资源维度）
```

## 4.3 选型：服务端多租户语境下的资源控制

> 关键差异：本机单用户，**烧的是开发者自己的钱**，失控最多卡自己一台机器；**服务端多租户，一个租户的失控循环 = 拖垮共享算力（noisy neighbor）+ 平台替它买单账单**。所以服务端的资源控制不止省钱，还要保证**公平性**和**可用性**。

| **维度** | **本机单用户** | **服务端多租户** |
| --- | --- | --- |
| **成本** | 烧自己的钱 只管省钱 | 烧平台账单 管公平+可用性 |
| **失控影响** | 卡自己一台 | 拖垮共享算力 noisy neighbor |
| **护栏维度** | 只管成本 | 成本+公平+可用性 三合一 |

**三合一的含义**（这是和三大 Agent 最本质的区别，面试必答）：

```Plaintext
成本护栏   ──别烧穿账单──▶              Token 预算（TPM）+ 省钱三层
公平性护栏 ──别让一个租户占满算力──▶    按租户配额 + 全局并发上限
可用性护栏 ──别让失控循环拖垮服务──▶    迭代预算 + 熔断 + 活跃度超时

→ 三大 Agent 只管"成本"（本机单用户）；
  公平性和可用性是服务端才有的新维度，照搬三大 Agent 会漏掉这两条。
```

**选型结论**：

```Plaintext
我们的资源控制 = 四道闸（在已有令牌桶之上叠加）：

  闸1【入口】 令牌桶限流（已有）        QPS 维度，按 userId（→ 升级为 tenantId）
  闸2【预算】 Token 预算（TPM，新增）    按 Token 计量，超预算拒绝/降级
  闸3【执行】 迭代预算 + 熔断（新增）    梯度警告 + 连续失败停
  闸4【卡死】 活跃度超时（新增）         只在静默超时才杀，不误杀长任务

  + 并发上限（以统一配置约束不同语言的执行器；下文为关键实现示例）
  + 省钱三层（Cache/压缩/按需加载，跨章：压缩在 ch1、按需加载在 ch5）
```

### 4.5.2 闸1：令牌桶限流（已有，真·CAS 令牌桶）

> 现状诚实呈现：限流这道闸我们做得扎实——Java `TokenBucketLimiter` 和 Go `ratelimit.go` 都是真 CAS 令牌桶（按纳秒/毫秒时间戳补充令牌），不是固定窗口计数器。

```Java
// Java：TokenBucketLimiter（gateway/ratelimit/，真令牌桶）
// CAS 原子扣减 + refillTokens() 按纳秒时间戳补充
public synchronized boolean tryAcquire(String key) {
    refillTokens(nowNs());                 // 按经过时间补令牌
    if (tokens >= 1) { tokens -= 1; return true; }
    return false;
}
// RateLimitManager 三层维度：全局 + userId + (agentId，仅并发>50 时启用)
```

```Go
// Go：ratelimit.go 真令牌桶（atomic.Int64 CAS + 毫秒 refill）
func (t *TokenBucketLimiter) TryAcquire() bool {
    t.refill(time.Now().UnixMilli())        // 按经过毫秒补令牌
    for {
        cur := t.tokens.Load()
        if cur <= 0 { return false }
        if t.tokens.CompareAndSwap(cur, cur-1) { return true }
    }
}
// RateLimitFilter 两层维度：全局 + userId
```

```Python
import asyncio
import time

class TokenBucketLimiter:
    def __init__(self, capacity: float, refill_per_second: float) -> None:
        self.capacity = capacity
        self.tokens = capacity
        self.refill_per_second = refill_per_second
        self.updated_at = time.monotonic()
        self._lock = asyncio.Lock()

    async def try_acquire(self) -> bool:
        # 单进程异步并发用 Lock 保护“补充 + 扣减”这一组原子操作。
        async with self._lock:
            now = time.monotonic()
            elapsed = now - self.updated_at
            self.tokens = min(
                self.capacity, self.tokens + elapsed * self.refill_per_second
            )
            self.updated_at = now
            if self.tokens < 1:
                return False
            self.tokens -= 1
            return True
```

> 教学可点出的工程取舍：分布式版（Redis）目前用 `INCR + 1秒 pexpire` 的**固定窗口计数**实现（Java `RedisClient` 注释直言"用简单计数替代令牌桶"）。固定窗口精度略低于令牌桶（窗口边界有突刺），但分布式下实现简单——这是**工程取舍**，不是缺陷。扩展篇保持"本地令牌桶 + 分布式滑窗计数"的分层。

### 4.5.3 闸2：Token 预算（TPM，新增）

> 现状：限流是 QPS（按请求数），没有按 Token 计量。但一次"总结 10 万字文档"的请求和一次"你好"的请求，Token 消耗差千百倍——只按请求数限流，挡不住一个大请求烧穿预算。扩展篇补 Token 维度。

```Java
// Java：Token 预算守卫（按租户配额，超了降级或拒绝）
public class TokenBudgetGuard {
    // 调用 LLM 前预估 Token 扣预算；超预算 → 降级便宜模型或拒绝
    public Decision check(String tenantId, int estimatedTokens) {
        TenantQuota q = quotaManager.get(tenantId);          // etcd 下发的配额
        if (q.consumedTpm() + estimatedTokens > q.maxTpm()) {
            if (q.allowDowngrade()) return Decision.DOWNGRADE_MODEL; // 降级
            return Decision.REJECT;                                   // 拒绝
        }
        return Decision.ALLOW;
    }
    // 调用后用真实 usage 回填（prompt_tokens + completion_tokens）
    public void record(String tenantId, TokenUsage actual) { ... }
}
```

### 4.5.4 闸3：迭代预算梯度警告 + 连续失败熔断（升级 maxIterations=10）

> 现状：`BaseAgent.chatWithTools` 硬上限 10 次（Java/Go 一致），到顶只返回一句提示，无梯度警告、无连续失败熔断、循环体无 try/catch 兜底。扩展篇把它从"到顶才停"升级成"提前预警 + 失败兜底"。

```Java
// Java：迭代预算（90 次）+ 梯度警告 + 熔断器
public String chatWithTools(...) {
    int budget = config.getMaxIterations();        // 默认 90（原 10）
    int warn70 = (int)(budget * 0.7);              // 63 次
    int warn90 = (int)(budget * 0.9);              // 81 次
    int consecutiveFails = 0;
    for (int i = 0; i < budget; i++) {
        if (i == warn70) ctx.injectSystem("剩余迭代 30%，请收束");
        if (i == warn90) ctx.injectSystem("剩余迭代 10%，请尽快完成");
        try {
            ChatResponse r = model.chat(request);
            consecutiveFails = 0;                   // 成功就清零
            if (!r.hasToolCalls()) return r.text(); // 收敛 → 返回
        } catch (Exception e) {
            if (++consecutiveFails >= 3) {          // 连续失败熔断（=3）
                auditLog.fail("熔断：连续 3 次失败，停止重试");
                return "处理超时，已停止（避免无效重试）。";
            }
        }
    }
    return "达到迭代上限。";
}
```

```Go
// Go：迭代预算 + 梯度警告 + 熔断

        }

}
```

```Python
async def chat_with_tools(self, messages: list[Message]) -> str:
    budget = self.config.max_iterations
    warn_at = {int(budget * 0.7): "剩余迭代 30%，请收束",
               int(budget * 0.9): "剩余迭代 10%，请尽快完成"}
    consecutive_failures = 0

    for iteration in range(budget):
        if warning := warn_at.get(iteration):
            messages.append(Message.system(warning))
        try:
            response = await self.llm.chat_with_tools(messages, self.tool_defs)
        except Exception:
            consecutive_failures += 1
            if consecutive_failures >= 3:
                raise CircuitOpenError("连续三次失败，停止无效重试")
            continue

        consecutive_failures = 0  # 只有成功调用才清零
        if not response.tool_calls:
            return response.text
        messages.extend(await self.execute_tool_calls(response.tool_calls))

    raise IterationLimitError(f"达到迭代上限 {budget}")
```

### 4.5.5 闸4：活跃度超时（不是墙时钟）+ LLM 调用超时

> 现状：Java LLM 60s 超时（`LLMGateway`）；**Go 侧 **`openai.go`** 的 **`http.Client{}`** 没设 Timeout（chat 路径走 **`http.DefaultClient`**，Timeout=0，永不超时）**，且上游没有给 chat 调用加 context deadline。扩展篇统一为"活跃度超时 + 显式 context deadline"。

```Python
import asyncio
import time

async def run_until_idle(self) -> str:
    idle_deadline = time.monotonic() + self.config.idle_timeout_seconds
    for _ in range(self.config.max_iterations):
        if time.monotonic() > idle_deadline:
            raise IdleTimeoutError("任务长时间没有产生新进展")

        # wait_for 只限制单次模型调用；它和“整体无活跃”是两个不同边界。
        response = await asyncio.wait_for(
            self.llm.chat_with_tools(self.messages, self.tool_defs), timeout=60
        )
        if not response.tool_calls:
            return response.text
        await self.execute_tool_calls(response.tool_calls)
        idle_deadline = time.monotonic() + self.config.idle_timeout_seconds

    raise IterationLimitError
```

### 4.5.6 并发上限（关键实现示例）

> 现状：Java 有全局固定线程池（`globalMaxConcurrent` 默认 100）+ Lane 会话串行化；**Go 侧是裸 goroutine，**`GlobalMaxConcurrent`** 配置字段定义了（**`config.go`**）且 **`stage3.yml`** 写了 100，但全仓没有任何代码读取它**——定义了上限却没强制。扩展篇给 Go 补 worker pool，把这个孤立字段用起来。

```Go
// Go：全局并发上限（worker pool，把孤立配置字段用起来）
type ConcurrencyLimiter struct {
    sem chan struct{}                      // 容量 = globalMaxConcurrent
}
func NewLimiter(max int) *ConcurrencyLimiter {
    return &ConcurrencyLimiter{sem: make(chan struct{}, max)}
}
func (c *ConcurrencyLimiter) Run(task func()) {
    c.sem <- struct{}{}                    // 占一个槽（满了就等）
    go func() { defer func() { <-c.sem }(); task() }()
}
// gateway 初始化时 NewLimiter(cfg.GlobalMaxConcurrent)，每个请求 Run(...)
```

```Java
// Java：已有（gateway/AgentGateway.java）
this.executorService = Executors.newFixedThreadPool(
    config.getGlobalMaxConcurrent(),       // 默认 100
    r -> { Thread t = new Thread(r,"gw-worker"); t.setDaemon(true); return t; });
// + Lane 会话串行化（laneMaxConcurrent=1，防同 session 并发乱序）
```

```Python
class ConcurrencyLimiter:
    def __init__(self, maximum: int) -> None:
        self._semaphore = asyncio.Semaphore(maximum)

    async def run(self, operation: Callable[[], Awaitable[T]]) -> T:
        # Semaphore 满时请求在这里等待；无论成功、异常或取消都会释放槽位。
        async with self._semaphore:
            return await operation()

# Gateway 共享一个全局 limiter；同一 session 仍由 Lane 单独串行化。
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **全局并发上限** | 线程池（Java）/ semaphore worker pool（Go） | 防总量打满 |
| **会话串行化** | Lane（每 session CAS 锁） | 防同会话并发乱序 |
| **配置字段真生效** | Go 把 GlobalMaxConcurrent 接上 semaphore | 不留"定义了没用"的坑 |

## 4.6 面试答法

| **面试官问** | **标准答法** |
| --- | --- |
| **Agent 一次任务花多少 Token？怎么控？** | 四道闸：① 令牌桶限流（QPS+租户）② Token 预算（TPM，超了降级）③ 迭代预算 90 次（70%/90% 梯度警告）+ 连续失败熔断=3 ④ 活跃度超时。省钱还靠 Prompt Cache/压缩/工具按需加载。 |
| **工具/Skill 一多，成本怎么变？** | Token 二次方增长四源（上下文累加/工具schema/系统提示/thinking）。工具同时进上下文 >5-10 个系统性拉低决策（Anthropic 数据）。我们用 defer_loading 按需付 + 工具数阈值裁剪（接 Skill 渐进式披露，第 5 章）。 |
| **Agent 进死循环 / 工具一直失败怎么办？** | 死循环三层兜底：① 迭代预算硬顶（即使每轮成功也不能无限跑）② 连续失败熔断 =3 停（防工具反复失败）③ 活跃度超时（防卡死）。阈值生产标定（引 Claude Code BigQuery：1,279 会话连续失败 3,272 次 → 改 =3）。 |
| **超时怎么设？** | 活跃度超时，不是墙时钟——从最后工具调用完成计静默时长，只在"卡死不动"才杀，不误杀数据分析这类合法长任务。 |
| **多租户共用算力，一个租户跑飞怎么办？** | 这是服务端和本机工具的本质区别。按租户配额隔离（tenantId 维度的 QPS + TPM + 并发上限），一个租户吃满自己的配额就被限，拖不垮别人（防 noisy neighbor）。本机工具（Claude Code 等）烧开发者自己的钱，没有这个维度。 |
| **护栏写在哪层？** | 程序层，硬编码进执行循环——不靠提示词。令牌桶/熔断/超时都是程序逻辑，prompt injection 绕不过。 |
| **限流是令牌桶还是计数器？** | 本地是真令牌桶（CAS 按时间戳补令牌）；分布式版基于 Redis 计数（固定窗口，精度略低但实现简单）——工程取舍，分层保留。 |
| **Token 预算超了怎么办？** | 先降级到便宜模型（平滑），不是直接拒绝。配额按租户 etcd 下发，可动态调整不重启。 |

## 小结

1. **资源控制 = 三合一**：成本护栏（省钱）+ 公平性护栏（按租户）+ 可用性护栏（防失控）。服务端独有公平性维度，这是和三大 Agent 的本质区别。

1. **四道闸**：令牌桶（已有）→ Token 预算（TPM 新增）→ 迭代预算+熔断（升级）→ 活跃度超时（新增）。

1. **死循环三层兜底**：迭代预算硬顶 + 连续失败熔断=3 + 活跃度超时，各防一种失控。

1. **省钱写进默认**：Prompt Cache（系统提示冻结）/ Auto-Compact（70/90/98%）/ defer_loading（按需付），用户无感。

1. **阈值生产标定**：熔断=3、迭代 90 不是拍脑袋，是真实故障数据反推（面试加分）。

1. **护栏在程序层**：全硬编码进执行循环，不靠提示词，prompt injection 绕不过。
