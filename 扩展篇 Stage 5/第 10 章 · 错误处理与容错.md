# 第 10 章 · 错误处理与容错：错误分类 + 重试 + 熔断 + 降级 + 防假完成

> **为什么有这章**：原项目调用级容错基本空白——工具/LLM 调用无错误分类、无重试、无降级，失败要么全交模型、要么异常直接抛（第 4 章已补循环级熔断，但"单次调用失败怎么办"没人管），会出静默挂起、级联 Fallback 全家失效、假完成这些生产事故。这章补**错误分类（可恢复/不可恢复）+ 重试 + 熔断 + 降级（防级联）+ 防假完成 + 续跑**；对应学员反馈"调用工具失败处理"。

## 这篇讲什么

错误处理要解决的问题是：**单次调用失败怎么办——重试、降级、还是上报，以及怎么不让一次失败拖垮整条链**。别让一个临时超时变成无限重试烧穿配额，也别让主模型挂了把备用模型一起拖下水。

为什么服务端要单拎出来讲：本机的 Claude Code 这类工具，失败了用户自己重启就行，级联失效、静默挂起影响一个人；我们是多租户共用算力，一个会话静默挂 600 秒占住共享会话槽，一个 Provider 级联失效会波及所有租户——所以这里的容错不只是"自愈"，还是可用性护栏。这是这章和本机工具最大的不同。

**核心模型：一条调用失败的处理流水线。** 失败进来依次过几道关，每道挡一类问题：

```Plaintext
失败 → ①错误分类 → ②重试or上报 → ③熔断 → ④降级Fallback → ⑤防假完成 → ⑥续跑
       可恢复/不可恢复  退避+retry-after  =3,数据驱动  按Provider隔离   空回复检测   Checkpoint
```

**三个关键认知（想通这三个，这章就懂了）：**

- **失败决策方是分野，决定整套容错的稳健性**：把失败全交给模型（OpenClaw）看起来灵活，多重失败叠加时不可预测——静默挂起 600 秒、级联 Fallback 全家失效、删 sessions.json 失忆三连；程序先分类（Claude Code）才稳：临时故障自动重试、确定故障直接上报，模型只在程序画好的边界里决策。

- **降级不是配一串备用模型就行，冷却必须按 Provider 独立**：OpenClaw Issue #49732 的反面——Opus 限流把整个 Anthropic Provider 标记冷却，本无故障的 Sonnet 也连带不可用，三档 Fallback 同时失效。铁律是一个模型的失败不能传染同 Provider 的其他模型。

- **最危险的是"假完成"，不是报错**：Hermes bug #9400——工具执行成功但模型回复为空时，系统去捞上一轮旧文字当最终答案，再汇报"完成了"。容错必须检测空回复，不能默认"没报错就是成功"（见本章 §10.5.7）。

> 这是这章的骨架。错误分类树、Fallback 冷却状态机、空回复检测怎么落地，往下看 §10.2 起。**细节是用来查的，不用全记**；先把上面这条流水线和三个认知想清楚。

## 10.2 三大 Agent 的错误处理（重点：讲透）

### 10.2.1 核心问题：谁决定失败后怎么办

所有容错设计都回答一个问题：**失败后下一步由谁决定**。三大 Agent 的分歧根本在这：

```Plaintext
失败决策方（三档）：
   [全交模型]   失败注入上下文，模型自决重试/换法/上报（OpenClaw）
                → 灵活，但多重失败叠加时不可预测（静默挂起/级联/失忆）
   [程序先分类] 程序把失败分类，可恢复的自动重试，不可恢复的交模型（Claude Code）
                → 可预测、省配额、有兜底（最稳健）
   [粗粒度程序] 固定重试 N 次不分类，之后交模型（Hermes）
                → 简单，但权限错误也白白重试，且有"假完成"bug

   铁律：临时性故障（网络/限流）该程序自动重试；
        确定性故障（权限/格式/工具不存在）该直接上报，别浪费配额。
```

### 10.2.2 Claude Code —— 错误分类树 + 集中模块 + 数据驱动熔断（范本）

Claude Code 的核心：**程序先分类，限定模型边界**。所有接触模型 API 的逻辑收敛到一个模块（`QueryEngine.ts`，单文件 46,000 行），保证重试行为一致。

**熔断阈值的真实来历**（黄金论据，面试加分）：

```Plaintext
2026-02 BigQuery 生产分析发现的真实故障：
   1,279 个会话出现 50 次以上连续 Compaction 失败
   单会话最多重试 3,272 次
   每天浪费 ~25 万次 API 调用

   → 修复：MAX_CONSECUTIVE_AUTOCOMPACT_FAILURES = 3
   → 关键：阈值不是拍脑袋，是【生产日志反推】的
   → 教训：没有熔断，一个失败会话能烧 3,272 次重试
```

> 教学点：Claude Code 给出容错的黄金范式——① 失败分类（可恢复才重试）；② 集中模块（统一重试行为）；③ 熔断阈值用生产数据标定，不是经验值。

### 10.2.3 OpenClaw —— 全交模型（反面：静默挂起 / 级联 / 失忆）

OpenClaw 把失败完全交给模型，没有程序级分类、没有重试上限、没有强制通知。生产事故三连：

```Plaintext
OpenClaw 失败处理（反面教材）：
   ①【静默挂起】工具调用卡住（RPC 死锁/Provider 超时）
      Agent 静默挂起最长 600 秒（DEFAULT_AGENT_TIMEOUT_SECONDS=600）
      期间消息排队不处理、界面无活动、用户无感知
      Issue #8288：一天 3 次、累计 >8 小时宕机

   ②【恢复即失忆】唯一恢复方式 ──删除 sessions.json + 重启 Gateway──▶
                          代价：Agent 全部会话历史销毁
                          （对比 Claude Code/Hermes 任务清单落盘续跑）

   ③【级联 Fallback 失效】（Issue #49732，下一节专讲）
```

### 10.2.4 降级 Fallback 的级联失败教训（OpenClaw Issue #49732）

这是降级设计最经典的反面——**一个模型的失败传染了整个 Provider 的可用性**：

```Plaintext
OpenClaw 级联 Fallback 失效（Issue #49732）：
   配置三档 Fallback：Opus → GPT-4o → Sonnet
   ① Opus 限流
   ② 整个 Anthropic provider 被标记"冷却"
   ③ 结果：本无故障的 Sonnet 也【不可用】（被连带冷却）
   ④ 三个 Fallback 同时失效
   ⑤ 最终向用户吐出【原始错误日志】而非友好提示

   根因：一个模型的失败，传染了整个 Provider 的可用性状态
   → 降级的铁律：Fallback 要按【模型/Provider 独立】隔离冷却，
                 不能让一个的失败拖垮同 Provider 的其他模型
```

> 教学点：降级不是"配一串备用模型"就完——**冷却状态必须按模型/Provider 独立**，否则一个限流能把同 Provider 全家拖下水。这是面试区分"配过 Fallback"和"真懂 Fallback"的分水岭。

### 10.2.5 Hermes —— 固定 3 次不分类（反面：假完成 bug）

Hermes 形式上有程序约束（重试 3 次），但粒度粗（不分类），还藏着一个危险的"假完成"bug：

```Plaintext
Hermes 失败处理：
   重试算法（固定 3 次、无退避、无分类）：
      attempt 1/3 → 2/3 → 3/3 → 放弃，告诉用户连接失败
      不管失败类型（网络/权限/超时）一律重试三次
      → 权限错误也白白重试 3 次（浪费配额）

   假完成 Bug（Issue #9400，未修复）：
      工具执行成功但模型回复为【空】时：
        去查上一轮是否留有旧文字
        若有 → 把旧文字当最终答案发出，结束任务
      旧文字属于上一轮、当前任务实际未完成
      但系统汇报"完成了"，无任何提示
      → 最危险的一类【静默失败】（见本章 §10.5.7）
```

> 教学点：Hermes 的"假完成"和本章 §10.5.7 行为审计（自我欺骗/任务替代）是一类——**Agent 把"没干完"报成"干完了"**。容错必须检测空回复，不能默认"没报错就是成功"。

### 10.2.6 会话恢复：任务状态 vs 对话历史分离

失败后能不能续跑，取决于**状态怎么存**。三家对比直接决定会话恢复：

```Plaintext
崩溃/失败后的恢复：
   OpenClaw    ──删 sessions.json──▶ 销毁全部历史，失忆（无法续跑）
   Claude Code ──任务清单落盘──▶ 从断点续跑（Tasks 持久化）
   Hermes      ──全历史入数据库──▶ 从断点续跑

   关键设计：任务状态（已完成的工具/中间产物/当前步骤）
             要和【对话历史】分离存储
   → 对话可丢（压缩/清理），任务进度不能丢
   → 我们已有 Checkpoint（第 8 章），本章把它和错误恢复打通
```

| --- | --- | --- | --- |

| **错误分类** | 无 | 可恢复/不可恢复二分 | 无（一律重试） |

## 10.3 选型：服务端多租户语境下的容错

> 关键差异：本机单用户，**失败了自己重启，级联失败影响一个人**；**服务端多租户，静默挂起/级联失效影响多租户可用性**——一个会话挂 600 秒、一个 Provider 级联失效，波及所有租户。所以服务端的容错不只是"自愈"，还是**可用性护栏**。

| **维度** | **本机单用户** | **服务端多租户** |
| --- | --- | --- |
| **失败影响** | 影响一人 | 波及所有租户可用性 |
| **级联失效** | 拖垮自己 | 拖垮共享算力 |
| **静默挂起** | 卡自己 | 占共享会话槽 |

**服务端容错的三个独有要求**（面试可答）：

```Plaintext
级联隔离   Fallback 按 Provider 独立冷却（一个限流不拖垮全家）
槽位释放   静默挂起要被活跃度超时杀掉（释放共享会话槽，接 ch4）
续跑保数据 任务状态持久化（多租户不能"删 sessions.json 失忆"）
```

**选型结论**：

```Plaintext
我们的容错 = 错误分类 + 重试 + 熔断 + 降级 + 防假完成 + 续跑

  分类：错误分类器（可恢复/不可恢复）
  重试：可恢复的才重试（退避 + retry-after），不可恢复直接上报
  熔断：连续失败 =3 停（接 ch4 循环级熔断，本章是调用级）
  降级：Fallback 按 Provider 独立冷却（防级联 #49732）
  防假完成：空回复检测（见本章 §10.5.7）
  续跑：任务状态 vs 对话历史分离（接 ch8 Checkpoint）
```

### 10.5.3 错误分类器（可恢复/不可恢复，关键实现示例）

```Java
// Java：错误分类器（Claude Code 二分法）
public class ErrorClassifier {
    public ErrorType classify(Throwable e) {
        if (e instanceof RateLimitException)    return RECOVERABLE;  // 429
        if (e instanceof NetworkException)      return RECOVERABLE;  // 超时/503
        if (e instanceof AuthException)         return UNRECOVERABLE;// 403
        if (e instanceof BadRequestException)   return UNRECOVERABLE;// 400
        if (e instanceof ToolNotFoundException) return UNRECOVERABLE;// 工具不存在
        return e.isTransient() ? RECOVERABLE : UNRECOVERABLE;
    }
    public Duration retryAfter(Throwable e) { /* 读 429 的 retry-after 头 */ }
}
```

```Go
// Go：错误分类器
func Classify(err error) ErrorType {
    var rl *RateLimitError;   if errors.As(err, &rl) { return Recoverable } // 429
    var net *netError;        if errors.As(err, &net) { return Recoverable } // 超时/503
    var auth *AuthError;      if errors.As(err, &auth) { return Unrecoverable } // 403
    var bad *BadRequestError; if errors.As(err, &bad) { return Unrecoverable } // 400
    if isTransient(err) { return Recoverable }
    return Unrecoverable
}
```

```Python
def classify_error(error: Exception) -> ErrorType:
    if isinstance(error, (RateLimitError, TimeoutError, ServiceUnavailableError)):
        return ErrorType.RECOVERABLE
    if isinstance(error, (AuthError, BadRequestError, ToolNotFoundError)):
        return ErrorType.UNRECOVERABLE
    return ErrorType.RECOVERABLE if getattr(error, "transient", False) else ErrorType.UNRECOVERABLE
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **二分法** | 可恢复/不可恢复 | 临时故障重试，确定故障上报 |
| **429 读 retry-after** | 尊重服务端退避指示 | 不盲目重试加重限流 |
| **403/400 不重试** | 直接上报 | 省配额（权限错重试也没用） |

### 10.5.4 重试（退避 + retry-after，可恢复才重试，关键实现示例）

```Java
// Java：可恢复错误才重试，指数退避 + retry-after 上限
public class RetryPolicy {
    public <T> T withRetry(Callable<T> call) throws Exception {
        int maxRetry = 3;                          // 数据驱动（接 BigQuery =3）
        long backoff = 200;                        // 指数退避起点
        for (int i = 0; i <= maxRetry; i++) {
            try { return call.call(); }
            catch (Exception e) {
                if (classifier.classify(e) == UNRECOVERABLE) throw e;  // 不重试
                if (i == maxRetry) throw e;
                long wait = Math.max(backoff, classifier.retryAfter(e).toMillis());
                sleep(wait); backoff *= 2;         // 指数退避
            }
        }
        throw new RuntimeException("unreachable");
    }
}
```

```Go
// Go：可恢复才重试
func WithRetry(fn func() error) error {
    maxRetry, backoff := 3, 200*time.Millisecond
    for i := 0; i <= maxRetry; i++ {
        err := fn()
        if err == nil { return nil }
        if Classify(err) == Unrecoverable { return err } // 不重试
        if i == maxRetry { return err }
        wait := max(backoff, RetryAfter(err))
        time.Sleep(wait); backoff *= 2
    }
    return nil
}
```

```Python
async def with_retry(operation: Callable[[], Awaitable[T]]) -> T:
    backoff = 0.2

            return await operation()
        except Exception as error:
            if classify_error(error) is ErrorType.UNRECOVERABLE or attempt == 3:
                raise
            delay = max(backoff, retry_after_seconds(error))
            await asyncio.sleep(delay)
            backoff *= 2
    raise AssertionError("unreachable")
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **只重试可恢复** | 分类后才重试 | 省配额（权限错不重试） |
| **指数退避** | 200ms→400ms→800ms | 避免重试风暴 |
| **retry-after 优先** | 尊重 429 指示 | 不加重限流 |
| **上限 3 次** | 数据驱动 | 防OpenClaw式 3272 次 |

### 10.5.5 熔断（连续失败 =3，调用级，接 ch4）

> 第 4 章的熔断是"循环级"（ReAct 连续失败），本章是"调用级"（同一工具/LLM 反复失败）。两层叠加。

```Java
// Java：调用级熔断器（连续失败计数）
public class CircuitBreaker {
    private final AtomicInteger fails = new AtomicInteger();
    private static final int THRESHOLD = 3;        // 数据驱动（BigQuery）
    public boolean allow() { return fails.get() < THRESHOLD; }
    public void recordFail() {
        if (fails.incrementAndGet() >= THRESHOLD) {
            audit.fail("调用级熔断：连续 3 次失败，停止重试");
            trip();                                 // 熔断，强制上报
        }
    }
    public void recordSuccess() { fails.set(0); }  // 成功就清零
}
```

```Go
// Go：调用级熔断器
type CircuitBreaker struct{ fails int32 }
const threshold = 3
func (c *CircuitBreaker) Allow() bool { return atomic.LoadInt32(&c.fails) < threshold }
func (c *CircuitBreaker) RecordFail() {
    if atomic.AddInt32(&c.fails, 1) >= threshold { c.trip() }
}
func (c *CircuitBreaker) RecordSuccess() { atomic.StoreInt32(&c.fails, 0) }
```

```Python
class CircuitBreaker:
    def __init__(self, threshold: int = 3) -> None:
        self.threshold = threshold
        self.failures = 0

    @property
    def allows_call(self) -> bool:
        return self.failures < self.threshold

    def record_failure(self) -> None:
        self.failures += 1
        if self.failures >= self.threshold:
            raise CircuitOpenError("连续失败达到熔断阈值")

    def record_success(self) -> None:
        self.failures = 0
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **调用级 vs 循环级** | 本章调用级 + ch4 循环级 | 两层熔断 |
| **=3 阈值** | 数据驱动（BigQuery 3272→3） | 不拍脑袋 |
| **成功清零** | recordSuccess 复位 | 偶发失败不累积 |

### 10.5.6 降级 Fallback（按 Provider 独立冷却，防级联，关键实现示例）

> 核心：**冷却状态按 Provider 独立**，不让一个模型的失败拖垮同 Provider 全家（OpenClaw #49732 教训）。

```Java
// Java：降级路由，按 Provider 独立冷却（防级联）
public class FailoverRouter {
    private final Map<String, ProviderHealth> health = new ConcurrentHashMap<>();
    public ModelRoute choose(List<ModelRoute> fallbackChain, String tenantId) {
        for (ModelRoute m : fallbackChain) {
            ProviderHealth h = health.computeIfAbsent(m.provider(), k -> new ProviderHealth());
            if (!h.isCoolingDown()) return m;      // 该 Provider 没冷却 → 用它
            // 关键：Opus 限流冷却，不连带 Sonnet（同 Provider 但按模型独立判断）
        }
        return null;  // 全冷却 → 上报或降级到最便宜模型（接 ch4 超预算降级）
    }
    public void markFail(ModelRoute m) { health.get(m.provider()).coolDown(m.modelId()); }
}
```

```Go
// Go：按 Provider+模型 独立冷却
func (r *FailoverRouter) Choose(chain []ModelRoute, tenantID string) *ModelRoute {
    for _, m := range chain {
        h := r.health[m.Provider]
        if !h.IsCoolingDown(m.ModelID) { return &m } // Opus 冷却不影响 Sonnet
    }
    return nil // 全冷却 → 上报/降级
}
func (r *FailoverRouter) MarkFail(m ModelRoute) {
    r.health[m.Provider].CoolDown(m.ModelID)
}
```

```Python
def choose(self, chain: list[ModelRoute], tenant_id: str) -> ModelRoute | None:
    for route in chain:
        # 健康状态按 provider + model 隔离，一个模型冷却不拖垮整条供应商链路。
        if not self.health.is_cooling_down(route.provider, route.model_id):
            return route
    return None

def mark_failure(self, route: ModelRoute) -> None:
    self.health.cool_down(route.provider, route.model_id)
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **按 Provider+模型 独立冷却** | Opus 冷却不连带 Sonnet | 防级联（#49732 根因） |
| **全冷却上报** | 不吐原始错误给用户 | 友好提示（#49732 教训） |
| **接超预算降级** | TPM 超了也降级（ch4） | 成本护栏联动 |

### 10.5.7 防假完成与行为审计

> Hermes bug #9400：工具成功但回复为空 → 拿上轮旧文字当答案。容错必须检测空回复，不能默认"没报错=成功"。

```Java
// Java：空回复守卫
public class EmptyResponseGuard {
    public GuardResult check(ChatResponse r, ExecutionTrace trace) {
        if (r.isSuccess() && (r.text() == null || r.text().isBlank())) {
            audit.suspicious("空回复：工具成功但回复为空，疑似假完成（Hermes #9400）");
            return GuardResult.REJECT_AND_RETRY;   // 不拿旧文字糊弄，重试或上报
        }
        return GuardResult.PASS;
    }
}
```

```Go
// Go：空回复守卫

    if r.IsSuccess() && strings.TrimSpace(r.Text) == "" {
        audit.Suspicious("空回复，疑似假完成")

    }

```

```Python
def check(self, response: ChatResponse, trace: ExecutionTrace) -> GuardResult:
    if response.success and not response.text.strip():
        self.audit.suspicious("工具执行成功但最终回复为空，疑似假完成")
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **空回复检测** | 成功但空 → 拒绝 | 防假完成（#9400） |
| **不拿旧文字糊弄** | 重试或上报 | 防沉默失败 |
| **可疑落审计** | 记录 | 有据可查 |

**更广的"行为审计"——不只查空回复，还查"该成功的有没有真成功"。** 空回复只是最明显的假完成；更隐蔽的是**任务替代**（任务失败 → Agent 改用相近任务替代 → 自信报"完成"）。所以在 `chatWithTools` 结束后，再过一道独立校验：用一个**独立验证器**对照"原始意图 vs 实际执行轨迹"，检查 ① 原始任务必需的关键工具有没有真正成功执行过、② 有没有 error/空集被当成功往下传。关键是这个验证器**刻意不看模型的推理文字**（信息隔离），只看用户意图 + 工具调用序列 + 结果——这样 Agent 没法用流畅解释骗过它。这是比空回复检测更深一层的"假完成"防护。

```Java
// Java：行为审计（独立验证器，不看推理）
public AuditVerdict audit(String userIntent, ExecutionTrace trace) {
    for (ToolStep step : trace.steps())
        if (step.result().isErrorOrEmpty() && step.treatedAsSuccess())
            return AuditVerdict.SUSPICIOUS("沉默失败：" + step.tool());
    if (!intentCoverageChecker.covers(userIntent, trace))
        return AuditVerdict.SUSPICIOUS("任务替代：原始意图未被执行");
    return AuditVerdict.OK;
}
```

### 10.5.8 任务状态 vs 对话历史分离（断点续跑，接 ch8）

> 已有 Checkpoint（第 8 章 Memory + Redis）。本章强调：**任务状态和对话历史分离存储**——对话可丢（压缩/清理），任务进度（已完成工具/中间产物/当前步骤）不能丢。失败后从断点续跑，不失忆（反 OpenClaw 删 sessions.json）。

```Plaintext
状态分离存储：
   对话历史（DistributedMemory Redis）──可压缩/清理──▶ 可丢
   任务状态（Checkpoint）              ──持久化──▶ 不可丢
     · 已完成的工具调用
     · 中间产物
     · 当前 ReAct 步骤
   失败/崩溃 ──load Checkpoint──▶ 从断点续跑，不重来
```

### 10.5.9 声明式配置（etcd 动态容错策略）


## 10.6 面试答法

| **面试官问** | **标准答法** |
| --- | --- |
| **Agent 调工具失败怎么办？** | 程序先分类再决定：错误分类器把失败分可恢复（网络超时/429/503）和不可恢复（403/400/工具不存在）。可恢复的自动退避重试（读 retry-after），不可恢复的直接上报不重试（省配额）。连续失败 =3 触发熔断（调用级，接 ch4 循环级）。 |
| **重试几次？怎么退避？** | 上限 3 次（数据驱动——Claude Code 的 BigQuery 实践：没熔断一个会话重试了 3,272 次，每天浪费 25 万次 API）。指数退避（200→400→800ms），429 优先读 retry-after 头。只重试可恢复的，权限错不重试。 |
| **主模型挂了怎么办？** | 降级 Fallback（Opus→GPT4o→Sonnet）。关键：冷却状态按 Provider+模型独立——不能像 OpenClaw Issue#49732 那样，Opus 一限流把整个 Anthropic provider 冷却，连带没故障的 Sonnet 也不可用。一个模型失败不能传染同 Provider 全家。 |
| **工具卡住不返回怎么办？** | 活跃度超时（第 4 章）——从最后一次工具调用完成计静默时长，只在"卡死不动"才杀，不误杀长任务。服务端这还会释放共享会话槽（接 ch4）。对比 OpenClaw 静默挂起 600 秒占着不动的反面。 |
| **工具成功但回复为空怎么办？** | 空回复守卫——检测到"成功但空"不拿旧文字糊弄（Hermes bug #9400 就是空回复拿上轮旧答案当完成，最危险的静默失败）。拒绝并重试/上报，落行为审计（本章 §10.5.7）。不能默认"没报错就是成功"。 |
| **失败/崩溃后会话丢吗？** | 不丢。任务状态和对话历史分离存储——对话可压缩/清理，任务进度（已完成工具/中间产物/当前步骤）持久化到 Checkpoint（第 8 章 Redis）。崩溃从断点续跑。对比 OpenClaw"删 sessions.json 重启丢全部历史"的反模式。 |
| **错误处理写在哪层？** | 程序层，集中在 llm/tool 包（Claude Code 的 QueryEngine 思路——所有 API 调用收敛到一个模块，重试行为一致）。不靠提示词让模型自己决定——OpenClaw 那样多重失败叠加会不可预测。 |
| **服务端和本机的容错有什么不同？** | 服务端失败波及多租户可用性：① 级联失效拖垮所有租户（必须按 Provider 隔离）② 静默挂起占共享槽（必须活跃度超时释放）③ 失忆=丢多租户数据（必须 Checkpoint 续跑）。本机失败只影响自己，重启即可。 |

## 小结

1. **失败决策方是分野**：程序先分类（Claude Code）最稳；全交模型（OpenClaw）会静默挂起/级联/失忆。

1. **错误分类二分**：可恢复（429/超时/503）才重试，不可恢复（403/400/工具不存在）直接上报，省配额。

1. **熔断数据驱动**：=3 来自 BigQuery 生产数据（曾 3,272 次重试），不是拍脑袋。调用级（本章）+ 循环级（ch4）两层。

1. **降级防级联**：Fallback 按 Provider+模型独立冷却，一个失败不传染全家（#49732 教训）。

1. **防假完成**：空回复检测，不拿旧文字糊弄（Hermes #9400），见本章 §10.5.7 行为审计。

1. **任务状态 vs 对话历史分离**：对话可丢、任务不丢，Checkpoint 断点续跑（接 ch8）。
