# 第 2 章 · 多租户隔离：从"软隔离"到"租户级强边界"

> **为什么有这章**：原项目基本没做多租户隔离——会话、记忆、检索都没强制带 tenantId，多租户全靠业务层自觉，A 租户理论上能串到 B 的数据。这章补 **5 级隔离矩阵 + Pool 模型（partition key + 元数据 filter）+ tenantId 贯穿全链路**；这是服务端平台独有问题（三大 Agent 是本机单用户，根本不做多租户），对应学员反馈"AI 租户隔离"。

## 这篇讲什么

多租户隔离要解决的问题是：**A 租户的数据（向量库、记忆、配额）B 租户绝对看不到、也跑不进来**——不是"靠 sessionId 前缀软隔离"那种一戳就破的，而是从网关到存储每一层都强制按租户切分的强边界。

为什么这章服务端独有：本机的 Claude Code / OpenClaw / Hermes 是装在开发者自己电脑上的单用户工具，天然没有"别的租户"，三大 Agent 根本不做多租户。我们是统一部署在远端服务器、服务成千上万租户的平台——多租户不是加分项，是存在性问题：做不到，平台就不能上线。所以这章的完整矩阵是我们自己的设计，只能从三大 Agent 借"隔离思想"（session key 编码边界、default-deny、容器执行隔离），借不到现成方案。

**核心模型：5 级隔离矩阵 + tenantId 贯穿 + 三大资源按租户切。** 数据层选第 2 级（partition key + filter，Milvus 性价比之选），执行层第 4 级（容器），配额层每租户令牌桶：

**三个关键认知（想通这三个，这章就懂了）：**

- **tenantId 是根标识，强制必填、贯穿全链路**：从"Java 预留了空字段、Go 连字段都没有"升级为 `final`/必填 struct；网关 default-deny（无 tenant 直接 401），对标 OpenClaw 13.5 万实例暴露公网、63% 无认证的反面教材。隔离不能只在某一层，要端到端。

- **不上一租户一 collection，选 partition + filter**：1000 租户 = 1000 collection，管理和成本爆炸；Pool 模型（共享 collection + tenant_id filter）在 Milvus 上性能足够，是 SaaS 主流，大客户/强合规才升第 4/5 级。铁律：**tenant filter 必须在 retrieval 阶段强制，不能事后过滤**——事后筛既慢又可能泄漏。

- **三资源一起切，缺一个就漏**：向量库（filter）、记忆（key 前缀）、配额（令牌桶）——只切向量库不切记忆，A 还是能靠 sessionId 读 B 的会话；不切配额，一个租户跑飞就拖垮所有人（noisy neighbor）。三块必须同步设计，配额顺便解决了第 4 章的公平性。

> 这是这章的骨架。每一级隔离怎么落地、关键实现示例代码长什么样，往下看 §2.2 起。**细节是用来查的，不用全记**；先把上面这个矩阵和三个认知想清楚。

## 2.1 痛点：多租户是服务端平台的"存在性问题"

## 2.2 先认清现实：三大 Agent 不做多租户——我们能借鉴什么

<!-- 画板未能抓取（请把画板滚动到可见区域后重试，或在飞书里另存为图片手动插入） -->

> **这不是方法的短板，恰恰是方法的价值**：三大 Agent 有丰富设计的维度（记忆/Skill/工具/压缩），我们重借鉴；它们没做的维度（多租户，因为单用户），我们自己设计——而多租户正是面试官区分"本机玩具"和"服务端平台"的试金石。

### 2.2.1 OpenClaw —— session key 层级 = 上下文隔离的范本

OpenClaw 虽是单用户，但它的 **Gateway 用 session key 给每个对话一个唯一地址**，思路直接可借：

```Plaintext
session key 结构：  agent : main : channel : peer
                    │        │       │        │
                    │        │       │       对话方（如某个 Slack 频道/某个人）
                    │        │      渠道（Slack / Telegram / Discord）
                    │       主 Agent
                    Agent 实例

→ 每个对话天然有唯一地址 → Slack DM 与 Telegram 群组【不共享】会话历史
→ 这就是"逻辑隔离"的最小可用形态：用 key 的结构编码边界
```

但 OpenClaw 也是**反面教材**——它 **default-open（默认开放）**，把安全留给用户配置：

```Plaintext
default-open 的代价（真实数据）：
   13.5 万个 OpenClaw 实例暴露公网，63% 完全无身份认证
   ClawHavoc 事件：恶意 Skill 通过共享记忆文件实现跨 Session 持久化攻击
   Snyk 在技能市场找到 1,467 个恶意 Skill，其中 91% 同时含注入载荷 + 恶意代码

→ 教训：默认开放的隔离 = 没有隔离。多租户平台必须 default-deny（默认拒绝）。
```

### 2.2.2 Hermes —— fail-closed + 容器隔离 = 租户执行隔离的雏形

Hermes 的安全默认值与 OpenClaw 相反——**fail-closed（默认拒绝）**，并且把执行下推到容器层：

| **Hermes 容器后端隔离 Docker** | **作用** |
| --- | --- |
| **丢弃所有 Linux Capabilities** | 进程没有特权操作 |
| **PID 限制** | 防 fork bomb noisy neighbor |
| **命名空间隔离** | 容器内外互不可见 |
| **只读根文件系统** | 防持久化写入 |

> 这正是多租户"执行隔离"的雏形——每个租户的工具执行应该互相看不到、资源上互相不能挤占。

### 2.2.3 Claude Code —— OS 级沙箱 = 进程级隔离思想

Claude Code 用操作系统级原语做沙箱（Linux 的 bubblewrap / macOS 的 Seatbelt），核心思想"子进程继承约束"可借鉴：

```Plaintext
Claude Code 沙箱：
   主进程受约束（只能读写工作目录、网络走代理白名单）
        │ 派生
        ▼
   子进程【继承同样约束】  ← 关键：不能通过 spawn 子进程逃逸
```

| **三大 Agent 隔离思想** | **借鉴到多租户** | **不借鉴** |
| --- | --- | --- |
| **OpenClaw session key 层级** | 用 key 结构编码租户边界（tenant:agent:session） | default-open（改用 default-deny） |
| **OpenClaw default-open 反面教材** | 坚决 default-deny | — |
| **Hermes fail-closed** | 默认拒绝 | — |
| **Hermes 容器隔离（Cap drop/PID/namespace）** | 租户执行隔离 + 防 noisy neighbor | — |
| **Claude Code OS 沙箱 + 子进程继承** | 执行边界不可逃逸 | OS 级原语（我们服务端用容器足够） |

## 2.3 选型：服务端多租户的隔离矩阵

业界把多租户隔离分成 **5 级**，隔离强度和成本递增：

```Plaintext
隔离强度弱 ←──────────────────────────────────────────→ 隔离强度强
成本/运维低                                              成本/运维高

[1] 应用层共享    [2] 行级 RLS    [3] 共享库独立Schema   [4] 独立库/Collection   [5] 一租户一部署
  所有租户共用      同库同表加       同库不同 schema        每租户独立库/           每租户独立一套
  一个 app+DB       tenant_id 列                           collection             完整栈
```

| **级别** | **隔离强度** | **成本** | **运维** | **防 noisy neighbor** | **适用** |
| --- | --- | --- | --- | --- | --- |
| **1 应用层共享** | 弱（靠代码自觉） | 极低 | 简 | 弱 | demo / 内部工具 |
| **2 行级 RLS / filter** | 中（逻辑隔离） | 低 | 简 | 靠配额 | **中小型 SaaS 主流** |
| **3 独立 Schema** | 中高 | 中 | 中 | 中 | 中型、合规要求 |
| **4 独立库 / Collection** | 高 | 高 | 繁 | 强 | 大客户 / 金融医疗 |
| **5 一租户一部署** | 极强（物理） | 极高 | 极繁 | 极强 | 专属大客户 / 强合规 |

**三大 Agent 思想落到哪级**：OpenClaw 的 session key 是第 1 级（应用层逻辑隔离）；Hermes 容器隔离偏向第 4-5 级（执行层物理隔离）。我们要的是**数据层第 2 级 + 执行层第 4 级**的组合。

**选型结论（Pool 模型 + 执行隔离）**：

```Plaintext
数据层：第 2 级「Partition Key + metadata filter」  ← Milvus 性价比之选
        · 向量库：共享 collection，按 tenant_id 分区/过滤
        · Redis：key 前缀带 tenant
        · 关系数据：行级 tenant_id
执行层：第 4 级「容器隔离」                          ← 借鉴 Hermes
        · 工具执行进容器（Cap drop / PID limit / namespace）
配额层：每租户令牌桶                                  ← 防 noisy neighbor（接第 4 章）
大客户：按需升到第 4/5 级（独立 collection / 独立部署）
```

> 为什么不直接上一租户一 collection（第 4 级）？1000 个租户 = 1000 个 collection，管理/成本爆炸。Pool 模型（分区+过滤）在 Milvus 上性能足够，是 SaaS 主流。

## 2.4 适配：三大资源的租户隔离

### 向量库隔离：3 种范式

| **范式** | **隔离方式** | **成本** | **隔离强度** |
| --- | --- | --- | --- |
| **A 一租户一 Collection** | 物理隔离 | 高 N个collection | 最强 |
| **B 一 Collection 多 Partition** | Milvus partition_key | 中 | 中 |
| **C 共享 Collection + filter** | metadata filter | 低 | 依赖 filter 正确性 |

| **范式** | **隔离强度** | **检索性能** | **管理** | **选不选** |
| --- | --- | --- | --- | --- |
| **A 一租户一 collection** | 强 | 各自索引，快 | N 租户 N collection，繁 | 大客户/强合规 |
| **B 分区** | 中高 | 分区内快 | 中 | 中型 |
| **C partition key + filter** | 中 | filter 有微小开销 | 简，共享一套 | **我们选这个** |

### 记忆 key 空间分离（衔接第 1 章）

```Plaintext
短期会话：  tenant:{tid}:agent:{aid}:session:{sid}:history   ← Redis list，按会话
长期语义：  collection = agentforge_mem（共享）+ filter tenant_id  ← Milvus
热记忆：    tenant:{tid}:agent:{aid}:mem:hot                  ← Redis hash
   → 所有 key 强制带 tid，取数据时校验 tid 匹配，防 A 读 B
```

### 配额防 noisy neighbor

```Plaintext
租户A 跑了一个死循环 Agent，疯狂调 LLM
        │
        ▼
撞到 租户A 的配额（TPM/RPM/存储）
        │
        ▼
Redis+Lua 原子计数 → 超限拒绝 → 只影响 A，不波及 B/C/D
（详见第 4 章资源控制）
```

| **三大资源** | **本机 Agent（不隔离）** | **AgentForge（服务端多租户）** | **搬/改/弃** |
| --- | --- | --- | --- |
| **向量库** | 本地单 collection | 共享 collection + tenant filter | **改**（加 filter） |
| **记忆** | 本地文件 | Redis/Milvus key 带 tenant | **改**（加租户维度） |
| **执行** | 本机直跑 | 容器隔离（Cap drop/PID/namespace） | **搬**（Hermes 思想） |
| **配额** | 无 | 每租户令牌桶 | **新建**（服务端独有） |

## 2.5 落地：AgentForge 的多租户架构

### 2.5.1 总架构：tenantId 贯穿全链路

<!-- 画板未能抓取（请把画板滚动到可见区域后重试，或在飞书里另存为图片手动插入） -->

**tenantId 从"预留空字段"升级为"强制必填、贯穿全链路的根标识"**（关键实现示例）：

```Java
// Java：RequestContext 强制 tenantId
public class RequestContext {
    private final String tenantId;   // final，构造时必填，无默认值
    private final String userId;
    private final String sessionId;
    // 所有下游调用都能拿到 tenantId
}
// 网关 TenantFilter：无 tenantId 直接 401（default-deny）
```

```Go
// Go：RequestContext 强制 tenantId
type RequestContext struct {
    TenantID  string  // 必填
    UserID    string
    SessionID string
}
// 中间件：解析 token → 填 TenantID；为空 → 401
```

```Python
from dataclasses import dataclass

@dataclass(frozen=True, slots=True)
class RequestContext:
    # tenant_id 没有默认值，入口必须显式提供，避免请求落入“公共租户”。
    tenant_id: str
    user_id: str
    session_id: str
    agent_id: str

    def __post_init__(self) -> None:
        if not self.tenant_id.strip():
            raise PermissionError("missing tenant_id")

# 网关先验签并创建 RequestContext；构造失败直接返回 401，默认拒绝。
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **tenantId 强制必填** | final 字段 / 必填 struct | "隔离的根"必须强约束，不能是可选 |
| **default-deny** | 网关层无 tenant 即拒绝 | 对标 OpenClaw default-open 反面 |
| **贯穿全链路** | RequestContext 传递 | 隔离不能只在某一层，要端到端 |

### 2.5.2 向量库隔离（关键实现示例）

> 真正落地时，应让 Java、Go、Python 三种工程遵守同一套 VectorStore 隔离契约：检索必须携带 tenantId 过滤条件，清理必须限定知识库与租户范围。下面选用 Go 风格片段演示关键调用，不表示该能力已经合入任一语言工程。

```Java
// Java：检索强制带 tenant filter
SearchRequest req = SearchRequest.builder()
    .collection("agentforge_kb")
    .vector(queryVec)
    .topK(5)
    .expr("tenant_id == '" + ctx.tenantId + "'")   // ← 强制 filter，没这行 = bug
    .build();
```

```Go
// Go 风格示例：检索接口强制携带租户过滤条件
results, _ := vectorStore.SearchWithFilter(ctx, queryVec, 5,
    map[string]string{"tenant_id": ctx.TenantID})   // ← 强制
```

```Python
# Python：向量检索接口必须接收租户过滤条件，调用方不能省略。
results = await vector_store.search_with_filter(
    query_vector=query_vector,
    top_k=5,
    filters={"tenant_id": context.tenant_id},  # 强制隔离条件
)

# 删除同样必须同时限定 tenant_id 与 knowledge_base，禁止整库清理。
```

> 铁律（面试爱问）：**tenant filter 必须在 retrieval 阶段强制，不能事后过滤**。事后过滤 = 先把所有租户的候选都检索出来再筛，既慢又可能泄漏。

### 2.5.3 Redis key 前缀 + 配额

# Redis key 的第一段固定为租户，避免不同租户的会话发生键冲突。

## 2.6 面试答法

| **面试官问** | **标准答法** |
| --- | --- |
| **你们是多租户的吗？怎么隔离？** | 是。三大资源（向量库/记忆/配额）都按 tenant 切分；tenantId 是贯穿全链路的根标识，网关 default-deny。 |
| **向量库怎么隔离？** | Milvus 共享 collection + partition key + tenant_id filter，retrieval 阶段强制过滤（不事后筛）。大客户可升独立 collection。 |

| **行级 / schema / 独立库 / 独立部署怎么选？** | 5 级矩阵按隔离强度×成本权衡。我们选第 2 级（partition+filter）做数据层 + 第 4 级（容器）做执行层，大客户升 4/5 级。 |
| **noisy neighbor 怎么办？** | 每租户配额（RPM/TPM/存储），Redis+Lua 原子计数，超限只影响该租户。 |
| **你参考了谁？** | 三大 Agent 是单用户工具，不做多租户——多租户正是我们服务端平台的核心差异。我借鉴了 OpenClaw 的 session key 思想（用 key 结构编码边界）、Hermes 的 fail-closed + 容器执行隔离、Claude Code 的子进程继承约束；default-open（OpenClaw 13.5 万暴露）是反面教材。 |

## 小结

1. **认清现实**：三大 Agent 单用户、不做多租户；多租户是我们服务端平台的差异化，自己设计。

1. **借鉴思想**：session key 编码边界、default-deny、容器执行隔离、子进程继承约束。

1. **三资源隔离**：向量库 partition+filter、记忆 key 前缀、配额防 noisy neighbor。

1. **tenantId 是根**：强制必填、贯穿全链路、网关 default-deny。

1. **声明式不变**：knowledgeBase 带 tenant 归属 + 隔离范式 + 配额，etcd 动态下发。
