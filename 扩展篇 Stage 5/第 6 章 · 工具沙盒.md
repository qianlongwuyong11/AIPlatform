# 第 6 章 · 工具沙盒：三层防线 + ExecutionBackend + 服务端容器语义

> **为什么有这章**：原项目工具是进程内直接执行（ToolManager.execute → tool.execute），零沙盒——内置工具（计算器/搜索）是无副作用纯计算所以没出事，但一旦接有副作用的业务工具（改 DB、跑脚本），rm -rf、偷主机凭证、一个租户搞垮别人，全挡不住。这章补**三层防线（应用白名单 → 运行时 PEP → 容器隔离）+ ExecutionBackend（local/docker）**；对应学员反馈"工具沙盒具体实现"。

## 这篇讲什么

工具沙盒要解决的问题是：**工具在哪执行、爆炸半径多大、会不会被 prompt injection 绕过**——别让一个 `rm -rf` 端掉宿主，也别让一个租户的恶意工具碰到别人的数据。

为什么服务端要单拎出来讲：本机 dev-tool 的沙盒防"Agent 碰开发者宿主机"，靠的是 OS 内核原语（bubblewrap/Seatbelt），本机专属；服务端平台的沙盒防"租户间互窜 + 隔离执行 + 防打穿共享算力"——而且我们本来就在容器里跑，容器隔离对我们最天然。语义不同，照搬本机做法会出错。

**核心模型：三层防线 + ExecutionBackend 抽象。** 所有沙盒设计都回答"防什么"和"防线在哪层"，铁律是越靠近底层越难绕过：

```Plaintext
三层防线（安全递增，灵活性递减）：

  [应用层] 白名单 / 模式匹配 / 运行时 PEP       ← 能被 prompt injection 绕过
  [OS 层]  bubblewrap(Linux) / Seatbelt(macOS)  ← 内核级，绕不过（本机专属）
  [容器层] Docker Cap drop + PID limit + ns     ← 物理隔离，最强（服务端最适用）

  执行后端 ExecutionBackend：local / docker / ssh ——"工具是什么"和"在哪跑"解耦
  容器后端跑时跳过应用层审批（安全已下推到基础设施层）
```

**三个关键认知（想通这三个，这章就懂了）：**

- **安全护栏越靠近底层越难绕过**：应用层（白名单/模式匹配）能被 prompt injection 骗模型绕过；OS 层（bubblewrap/Seatbelt 内核级）不受 LLM 影响；容器层（Cap drop + PID limit + namespace）物理隔离最强。所以危险命令检测要写在程序层，但兜底要靠容器。

- **"工具是什么"和"在哪执行"要解耦**：ExecutionBackend 抽象（local/docker/ssh）让同一套工具定义换 backend 就换执行环境；容器后端直接跳过应用层审批，因为容器本身就是安全边界——把安全责任从应用层下推到基础设施层。

- **服务端的爆炸半径是"租户间互窜"**：本机一个用户没有互窜问题；服务端 A 租户的工具不能碰 B 租户的文件/记忆/凭证，所以每租户/Agent 独立容器或命名空间。再加输出侧防线（返回值 >50K 字符外部化为 2KB 摘要）——爆炸半径不只是"能改什么文件"，还包括"能往上下文灌多少 Token"。

> 这是这章的骨架。三层防线各自怎么配、ExecutionBackend 怎么抽象、容器后端怎么跳过审批，往下看 §6.2 起。**细节是用来查的，不用全记**；先把"越底层越难绕过 + 执行解耦 + 容器即边界"这三件事想清楚。

## 6.2 三大 Agent 的工具沙盒（重点：讲透）

### 6.2.1 核心问题：沙盒防什么 + 防线在哪层

所有沙盒设计都回答两个问题：**防什么**（文件/网络/凭证/进程），**防线在哪层**（应用层/OS 层/容器层）。三大 Agent 的分歧就在防线位置：

```Plaintext
防线三层位置（安全强度递增，灵活性递减）：

  [应用层] 白名单 / 模式匹配 / 事件拦截
     → 能被 prompt injection 绕过（诱导模型生成绕过逻辑）
  [OS 层]   bubblewrap / Seatbelt（内核级文件系统/进程隔离）
     → 不受 LLM 影响，绕不过
  [容器层]  Docker Cap drop + PID limit + 命名空间
     → 物理隔离，最强

  铁律：安全护栏越靠近底层越难绕过。
       Prompt injection 能骗模型忽略应用层指令，但没法让 OS 撤销文件系统隔离。
```

### 6.2.2 Claude Code —— OS 级沙箱（bubblewrap/Seatbelt）

Claude Code 的核心：**用户不该需要成为安全专家才能安全用 Agent**，沙盒内置在架构里。基于 **OS 内核原语**（不是应用层包装）：

```Plaintext
Claude Code 沙箱技术栈（OS 级）：
   Linux  ──bubblewrap──▶  内核级隔离
   macOS  ──Seatbelt───▶  内核级隔离

   文件系统隔离：
      Agent 只能读写【当前工作目录】
      系统文件 / 家目录其他部分 / SSH 密钥 ──访问被拒──▶
      派生的子进程【继承同样约束】（继承式隔离）

   网络隔离：
      所有网络请求必须过【沙箱外代理服务器】
      代理只放行【预批准域名】
      Agent 无法直连未知主机

   核心价值：即使 prompt injection 成功，损害锁在沙箱内——
            被攻陷的 Agent 既偷不到 SSH 密钥，也发不出数据
```

```Plaintext
量化收益（Anthropic 内部测试）：
   沙箱使需权限确认的操作数 ──减少 84%──▶
   → 更安全【且】更少打扰（不是"更安全=更烦人"）
```

> 教学点：Claude Code 的沙箱是"防 Agent 碰**开发者宿主机**"——因为它是本机 dev-tool。这套 OS 级原语（bubblewrap/Seatbelt）是本机专属的，服务端要在容器层实现等价语义（见 §6.4）。

### 6.2.3 Hermes —— 六执行后端 + 容器即边界（最贴近服务端）

Hermes 把"工具是什么"和"工具在哪执行"**解耦**——这是对服务端最有启发的设计。六种执行后端：

```Plaintext
Hermes 六执行后端（ExecutionBackend）：
   local       本机直接执行（默认）
   docker      容器隔离
   ssh         远程 SSH 执行
   daytona     云端开发环境
   singularity HPC 容器（科学计算）
   modal       Serverless GPU

   → 同一套工具定义，换 backend 就换执行环境
   → 安全等级（local < docker < cloud）与能力需求（GPU/HPC）可独立调整
   → 在 docker 后端跑同一工具集，就获得容器级隔离，无需改工具定义
```

**容器后端跳过审批**（关键设计模式，安全下推）：

```Plaintext
运行在 Docker/Modal/Daytona 后端时：
   危险命令审批检查【被跳过】
   → 因为容器本身就是安全边界
   → 容器内破坏性命令影响不到宿主
   → "把安全责任从应用层下推到基础设施层"

   容器隔离配置（Docker）：
   · 只读根文件系统（可选）
   · 丢弃所有 Linux Capabilities（Cap drop）
   · PID 限制（防 fork bomb）
   · 命名空间隔离（namespace）
```

**危险命令审批**（应用层兜底，非容器时用）：

```Plaintext
危险模式库检测：递归删除 / 权限修改 / sudo 使用 …
approvals:
   mode: manual    # manual（默认）/ smart（AI辅助）/ off（YOLO）
   timeout: 60     # 超时 ──默认拒绝──▶（fail-closed，不是放行）
```

> 教学点：Hermes 的"容器即安全边界 + 跳过审批"对服务端特别适用——**我们本来就在容器里跑**，让每个租户/Agent 的工具执行进独立容器，租户间物理隔离，比本机 dev-tool 更天然。

### 6.2.4 OpenClaw —— 应用层事件扩展（可选，反面）

```Plaintext
OpenClaw 工具拦截：
   机制本身正确——事件驱动扩展点，工具执行前触发事件，扩展可订阅拦截
   程序级拦截，不会被 prompt injection 绕过
   但：可选、非默认启用，需主动配置扩展

   后果（ClawHavoc）：
   默认无 Shell 白名单、无审批、无凭证限制
   → 装一个 Skill = 执行未知第三方代码 + 拿主机完整权限
   → ClawHavoc：恶意 Skill 偷 API Key，污染 MEMORY.md 跨 Session 持久化
   → 反面教材：机制对，默认值致命
```

### 6.2.6 输出侧防线：大返回值外部化

沙盒不只是"执行侧"隔离，还有"输出侧"防线——**工具返回值太大时会撑爆上下文**：

```Plaintext
工具返回值外部化（Claude Code 硬约束）：
   返回内容 > 50,000 字符 ──自动写临时文件──▶
   上下文只注入 2KB 摘要 + 引用句柄
   Agent 后续用 Read 工具按需回查

   为什么算"沙盒"：
   工具的爆炸半径不只是"能改什么文件"，还包括"能往上下文灌多少 Token"
   → 一个返回 50 万字符的搜索结果，和 rm -rf 一样会搞垮 Agent（Lost in the Middle）
   → 输出外部化 = 限制工具对上下文的"写入半径"
```

| **维度** | **OpenClaw** | **Claude Code** | **Hermes** |
| --- | --- | --- | --- |
| **防线层** | 应用层（事件，可选） | OS 层（bubblewrap/Seatbelt） | 容器层（六后端） |
| **文件隔离** | 无默认 | 工作目录限定 + 子进程继承 | 容器内 |
| **网络隔离** | 无默认 | 沙箱外代理 + 预批准域名 | 容器内 |

| **量化** | ClawHavoc 灾难 | 确认数 -84% | — |

## 6.3 选型：服务端多租户语境下的沙盒

> **本章最关键的认知**：本机 Agent 沙盒防"Agent 碰**开发者宿主机**"；**服务端平台沙盒防"租户间互窜 + 隔离执行 + 防打穿共享算力"**。语义完全不同。而且——**我们本来就在容器里跑**，Hermes 的"容器即边界"对我们最天然。

| **维度** | **本机三大Agent** | **服务端AgentForge** |
| --- | --- | --- |
| **沙盒语义** | 防Agent碰开发者宿主机 | 防租户间互窜+防打穿算力 |
| **手段** | bubblewrap/Seatbelt | 容器/namespace隔离 |
| **适配** | OS原语本机专属 | 本来就在容器里 |

**服务端沙盒的三个独有目标**（面试必答）：

```Plaintext
防租户互窜   A 租户的工具执行，不能访问 B 租户的文件/记忆/凭证
             → 每租户/Agent 独立容器或命名空间（接第 2 章）
隔离执行     有副作用的工具（跑脚本/装包）在隔离环境跑，不污染宿主
             → ExecutionBackend = docker/容器
防打穿算力   一个工具 fork bomb / 跑死循环，不能拖垮共享宿主
             → 容器 PID limit + CPU/内存 limit（接第 4 章资源控制）
```

**选型结论**：

```Plaintext
我们的工具沙盒 = ExecutionBackend 抽象 + 三层防线 + 输出外部化

  执行：ExecutionBackend（local 教学版 / docker 生产 / ssh 远程）
  防线：① 应用白名单（角色绑，不进 schema，接第3章）
        ② 运行时 PEP（危险命令模式匹配，fail-closed）
        ③ 容器隔离（Cap drop + PID limit + namespace）
  跳过：容器后端跑时，简化应用层审批（安全已下推）
  输出：大返回值 >50K 字符 → 临时文件 + 2KB 摘要引用
```

### 6.5.2 现状：工具进程内直接执行（诚实呈现）

> 现状：工具进程内直接执行（`ToolManager.execute → tool.execute(args)`），零沙盒、零执行后端抽象。内置工具（Calculator/DateTime/DataAnalyzer/WebSearch）是无副作用纯计算，进程内合理；但要支持"有副作用的业务工具"（改 DB、跑脚本、调外部 API），就必须加沙盒。

```Java
// Java 现状：ToolManager 直接执行（无沙盒层）
public ToolResult execute(RequestContext ctx, String name, Map args) {
    Tool tool = registry.get(name);
    // 第3章已加：白名单 + PEP + HITL（应用层防线）
    return tool.execute(args);              // ← 进程内直接执行，无 ExecutionBackend
}
```

```Go
// Go 现状：直接执行
func (m *Manager) Execute(ctx *RequestContext, name string, args map[string]any) (*ToolResult, error) {
    t := m.tools[name]
    return t.Execute(args)                   // 进程内，无沙盒
}
```

```Python
async def execute(
    self, context: RequestContext, name: str, args: dict[str, object]
) -> ToolResult:
    tool = self.tools[name]
    # 这里仅完成应用层权限检查；随后仍在主进程直接执行，尚无沙盒隔离。
    await self.policy_guard.check(context, tool, args)
    return await tool.execute(args)
```

### 6.5.3 ExecutionBackend 抽象（解耦"是什么"和"在哪跑"，关键实现示例）

> 借鉴 Hermes 六后端，引入 ExecutionBackend 接口——工具定义不变，换 backend 换执行环境。

```Java
// Java：ExecutionBackend 抽象
public interface ExecutionBackend {
    ToolResult exec(Tool tool, Map<String,Object> args, SandboxSpec spec);
}
class LocalBackend  implements ExecutionBackend { /* 进程内（教学版）*/ }
class DockerBackend implements ExecutionBackend {
    public ToolResult exec(Tool t, Map args, SandboxSpec s) {
        // Cap drop + PID limit + 只读根 + CPU/内存 limit + namespace
        return containerRunner.run(t.containerImage(), args, s);
    }
}
class SshBackend    implements ExecutionBackend { /* 远程执行 */ }
// ToolManager 按配置选 backend
```

```Go
// Go：ExecutionBackend 抽象
type ExecutionBackend interface {
    Exec(t Tool, args map[string]any, spec SandboxSpec) (*ToolResult, error)
}
type LocalBackend struct{}    // 进程内（教学）
type DockerBackend struct{}   // 容器隔离
type SSHBackend struct{}      // 远程

func (b *DockerBackend) Exec(t Tool, args map[string]any, s SandboxSpec) (*ToolResult, error) {
    // Cap drop + PID limit + readonly root + CPU/mem limit + namespace
    return b.runner.Run(t.ContainerImage(), args, s)
}
```

```Python
from typing import Protocol

class ExecutionBackend(Protocol):
    async def execute(
        self, tool: Tool, args: dict[str, object], spec: SandboxSpec
    ) -> ToolResult: ...

class DockerBackend:
    def __init__(self, runner: ContainerRunner) -> None:
        self.runner = runner

    async def execute(self, tool: Tool, args: dict[str, object], spec: SandboxSpec) -> ToolResult:
        # runner 负责 capability、PID、只读根目录、CPU/内存与 namespace 限制。
        return await self.runner.run(tool.container_image, args, spec)

# ToolManager 只依赖 ExecutionBackend，不关心任务在本地、容器还是远端执行。
```

| **设计点** | **方案** | **教学价值** |
| --- | --- | --- |
| **接口抽象** | ExecutionBackend（local/docker/ssh） | 工具定义与执行环境解耦 |
| **同工具换后端** | 换 backend 换隔离强度 | 灵活（教学 local / 生产 docker） |
| **容器镜像** | 工具带 containerImage 字段 | 有副作用工具的隔离单元 |

### 6.5.4 防线②③：危险命令模式匹配 + 容器隔离（关键实现示例）

```Java
// Java：危险命令模式匹配（程序级，fail-closed）
public class DangerPatternMatcher {
    private static final List<Pattern> DANGER = List.of(
        Pattern.compile("rm\\s+-rf"), Pattern.compile("sudo\\s"),
        Pattern.compile("chmod\\s+[0-7]{3,4}"), Pattern.compile(":\\(\\)\\s*\\{")); // fork bomb
    public Decision check(String command) {
        for (Pattern p : DANGER)
            if (p.matcher(command).find()) return Decision.REQUIRE_APPROVAL;
        return Decision.ALLOW;
    }   // 不靠 Prompt，纯模式匹配，prompt injection 绕不过
}
```

```Go
// Go：危险命令模式匹配 + 容器隔离 spec
var dangerPatterns = []*regexp.Regexp{
    regexp.MustCompile(`rm\s+-rf`), regexp.MustCompile(`sudo\s`),
    regexp.MustCompile(`:\(\)\s*\{`), // fork bomb
}
func checkDanger(cmd string) Decision {
    for _, p := range dangerPatterns {
        if p.MatchString(cmd) { return RequireApproval }
    }
    return Allow
}
// 容器隔离 spec（防租户互窜 + 防打穿算力）
type SandboxSpec struct {
```

```Python
DANGER_PATTERNS = tuple(
    re.compile(pattern) for pattern in (r"rm\s+-rf", r"sudo\s", r":\(\)\s*\{")

def check_danger(command: str) -> Decision:
    # 判定写在程序层；即使 Prompt 被注入也不能跳过。
    return (
        Decision.REQUIRE_APPROVAL
        if any(pattern.search(command) for pattern in DANGER_PATTERNS)
        else Decision.ALLOW
    )
```

## 6.6 面试答法

| **面试官问** | **标准答法** |
| --- | --- |
| **工具沙箱怎么做的？** | 三层防线：① 应用白名单（角色绑，未授权不进 schema）② 运行时 PEP（危险命令模式匹配，程序级 fail-closed）③ 容器隔离（Docker Cap drop + PID limit + namespace）。加输出外部化（返回值 >50K 落临时文件，上下文只留 2KB 摘要）。 |
| **这些防线能被 prompt injection 绕过吗？** | 应用层能（诱导模型生成绕过逻辑），所以关键防线下推到基础设施层——容器级约束（Cap drop/PID limit）是 OS 级的，不受 LLM 影响，绕不过。Prompt injection 能骗模型忽略应用层指令，没法让 OS 撤销容器隔离。 |
| **沙盒防什么？** | 服务端和本机工具语义不同：本机（Claude Code 等）防 Agent 碰开发者宿主机（bubblewrap 限工作目录）；我们服务端防租户间互窜 + 隔离执行 + 防打穿共享算力——每租户/Agent 独立容器，A 碰不到 B。 |
| **工具在哪里执行？** | ExecutionBackend 抽象，解耦"工具是什么"和"在哪跑"：local（教学）/ docker（生产隔离）/ ssh（远程）。同工具换 backend 换隔离强度，工具定义不变。 |
| **一个租户的恶意工具会不会影响别人？** | 不会。每租户/Agent 独立容器/namespace（物理隔离）+ 容器 Cap drop/PID limit（防 fork bomb 打穿宿主）+ 资源 limit（接第 4 章）。容器即边界，互窜不了。 |
| **容器里跑时为什么能跳过审批？** | 容器本身就是安全边界——容器内破坏性命令影响不到宿主，也碰不到别的租户。所以容器后端时简化应用层审批（安全已下推到基础设施层）。服务端本来就在容器里，这套最天然。 |
| **工具返回值很大怎么办？** | 输出外部化——返回 >50K 字符自动落临时文件，上下文只注入 2KB 摘要 + 引用，Agent 按需 Read 回查。这限制工具对上下文的"写入半径"，防 Lost in the Middle（接第 7 章 RAG）。 |
| **危险命令怎么检测？** | 程序级模式匹配（rm -rf/sudo/fork bomb/chmod 正则库），不靠模型判断。超时 fail-closed（默认拒绝，不放行）。 |

## 小结

1. **沙盒语义服务端不同**：本机防碰宿主，服务端防租户互窜 + 隔离执行 + 防打穿算力——这是部署语境前提最尖锐的一章。

1. **三层防线**：应用白名单 → 运行时 PEP（模式匹配）→ 容器隔离，安全递增、越底层越绕不过。

1. **ExecutionBackend 解耦**：local/docker/ssh，"工具是什么"和"在哪跑"分离。

1. **容器即边界**：服务端本就在容器里，每租户独立容器 + Cap drop/PID limit，物理隔离 + 跳过应用层审批。

1. **安全下推基础设施层**：应用层能被 injection 绕过，容器级不能——关键防线放底层。

1. **输出侧也是沙盒**：大返回值外部化（50K→2KB），限制工具对上下文的写入半径。
